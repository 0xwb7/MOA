# ADR-003: 정기 발송을 준비 단계와 발송 단계로 나눈다

- 상태: 제안 (초안)
- 날짜: 2026-11-22
- 관련 코드: `DigestPreparer`, `DigestService`, `DigestWriter`, `DigestScheduler`, `DigestRecovery`, `TeamLocks`

## 배경

MOA는 팀별 GitHub 변경을 수집하고, LLM으로 요약해서, 오전 9시와 오후 9시에 팀 PM에게 Discord로 보낸다.

가장 중요한 약속은 이것이다.

> 요약을 얼마나 잘하든, 정해진 시각에 메시지는 반드시 정각에 발송된다.

지금까지는 수집 → 요약 → 저장 → 발송이 한 메서드(`DigestService.sendTeam`) 안에서 이어졌다.

- 이 구조에서는 발송 시각이 가장 느린 단계에 묶인다. 요약은 OpenAI 응답이 늦으면 재시도까지 최대 3분쯤 걸린다.
- 준비한 내용은 메모리(`PreparedDigest`)에만 있었다. 그래서 중간에 서버가 재시작되면 사라졌다.

## 선택지

### A. 9시에 한 번에 처리한다 (기존 방식 유지)

- 장점: 구조가 단순하다. 9시 직전까지의 변경이 모두 들어간다.
- 단점
  - 발송 시각이 GitHub과 OpenAI의 응답 속도에 묶인다. 팀이 여러 개면 순서대로 밀려서, 마지막 팀은 몇 분 늦게 받는다.
  - 9시에 OpenAI가 느리거나 장애가 나면 "정각 발송"을 지킬 방법이 없다.
  - 처리 도중 재시작하면 그 회차를 복구할 기록이 없다.

### B. 준비(8:30)와 발송(9:00)을 나눈다 (채택)

- 8:30(20:30)에 수집과 요약을 끝내고, 발송할 내용 전부를 DB에 READY로 저장한다.
- 9:00(21:00)에는 저장된 것을 보내기만 한다.

## 결정

B를 채택한다.

### 회차와 상태

- **회차(cycle)는 발송 예정 시각(`scheduledFor`)으로 식별한다.**
  - `(team_id, scheduled_for)`에 유일 제약을 건다.
  - 정기 회차는 `SCHEDULED`, `/발송테스트`는 지금 시각을 회차로 쓰는 `MANUAL`이다.
- **Digest:** `PREPARING → READY → SENT / FAILED`
- **ChangeBatch:** `COLLECTED → PREPARED → SENT`
  - 발송이 실패하거나 준비가 취소되면 `PREPARED → COLLECTED`로 돌아가 다음 회차에 포함된다.
- **READY 시점에 저장하는 것:** 헤더 텍스트, 멘션 대상, 항목(DigestItem)을 모두 DB에 저장한다.
  - 메시지 분할은 발송 시점에 DB 내용으로 다시 계산한다.
  - 그래서 준비와 발송 사이에 재시작해도 보낼 수 있다.

### 준비 단계 (8:30)

1. 모든 팀에 대해 수집 → 요약 → READY 저장을 한다. 변경이 없으면 `NO_CHANGE`를 READY로 저장한다.
2. 팀 작업은 고정 3스레드 실행기에서 돈다. 동시에 준비하는 팀은 최대 3개다(OpenAI 요청 한도 고려).
3. 마감(발송 2분 전, 8:58)까지 끝나지 않은 팀은 작업을 취소하고 LLM 없이 변경 목록(FALLBACK)으로 READY를 만든다.
4. 한 팀이 실패해도 다른 팀의 준비는 계속된다.

### 발송 단계 (9:00)

- 회차의 READY를 보낸다.
- READY가 없는 팀은 발송 시점에 LLM 없이 즉석 fallback(또는 NO_CHANGE)을 만들어 바로 보낸다. 해당하는 경우는 이렇다.
  - 준비가 실패한 경우
  - 준비 중에 서버가 재시작된 경우
  - 아직 PREPARING인 경우

## 반드시 발송을 보장하는 방법

1. **발송 단계는 외부 API를 기다리지 않는다.**
   - GitHub이나 OpenAI를 부르지 않고, DB에 이미 있는 READY나 COLLECTED 배치만 쓴다.
   - 그래서 외부 장애가 9시 발송을 막지 못한다.
2. **READY가 없어도 보낸다.** 즉석 fallback이 준비 실패, 마감 초과, 재시작을 모두 흡수한다.
3. **조건부 상태 갱신으로 경쟁을 막는다.**
   - READY로 바꾸는 쿼리: `UPDATE … SET status = READY WHERE id = ? AND status = PREPARING`
   - 늦게 끝난 준비 작업은 이 UPDATE가 0행이라 결과를 저장하지 않고 버린다.
   - 이 UPDATE가 잡은 행 잠금 덕분에, 경쟁하는 쪽은 커밋된 상태만 본다.
4. **중복 발송을 막는다.** 발송은 `send_started_at`을 조건부로 채워 선점한다(`READY AND send_started_at IS NULL`).
5. **준비가 발송을 막지 않는다.**
   - 스프링 스케줄러 스레드는 트리거만 맡는다.
   - 준비는 코디네이터 1스레드와 준비 실행기 3스레드에서, 발송은 팀별 가상 스레드에서 돈다.
   - 스케줄러 풀도 2로 늘려 둔다.
6. **팀 락은 짧게만 기다린다.**
   - 준비, `/발송테스트`, `/수집테스트`는 같은 팀이 처리 중이면 바로 거절된다.
   - 발송 단계만 최대 30초 기다리고, 그래도 못 잡으면 락 없이 진행한다.
   - 락은 중복 LLM 호출을 막는 최적화이고, 정확성은 3번과 4번(DB)이 보장한다.
7. **재시작하면 복구한다.** 발송 시각이 지났는데 SENT가 아닌 정기 회차를 이렇게 처리한다.
   - 30분 이내면 늦게라도 보내고 WARN 로그를 남긴다.
   - 30분이 넘었으면 FAILED로 닫고 배치를 COLLECTED로 돌려 다음 회차에 포함한다.
   - 서버가 꺼져 있어 회차 기록조차 없는 경우도 같은 규칙으로 처리한다.
8. **운영 알림을 남긴다(`OpsNotifier`).** 대상은 이렇다.
   - 준비 실패
   - 마감 초과 fallback
   - 발송 시점 즉석 fallback
   - 발송 실패
   - 재시작 복구(늦은 발송, 포기)
   - 지금은 로그만 남기고, 다음 작업에서 운영진 장애 알림 채널로 보낸다.

## 감수하는 것

- **구조가 복잡해진다.**
  - 회차 상태, 배치 상태, 조건부 갱신, 마감 코디네이터, 재시작 복구가 생긴다.
  - 상태 전이는 `DigestWriter` 한 곳에 모으고, H2 통합 테스트(`DigestCycleTest`)로 시나리오별로 검증한다.
- **8:30 이후의 변경은 다음 회차로 넘어간다.**
  - 8:31에 push한 커밋은 9:00 메시지에 없고 21:00 메시지에 들어간다.
  - PM이 받는 정보는 최대 30분 늦다.
- **fallback 비율이 늘 수 있다.** 마감이나 장애 때 LLM 요약 대신 커밋 목록이 간다.
  - 품질보다 정각 발송을 우선한 결과다.
  - `/회차상태`와 운영 알림으로 얼마나 자주 그러는지 볼 수 있다.
- **최소 1회 전달이다.** 발송 도중에 서버가 죽으면 복구 시 다시 보내므로 같은 메시지가 두 번 갈 수 있다. 놓치는 것보다 중복이 낫다고 판단했다.

## 운영 메모

- **cron은 설정으로 바꿀 수 있다.** `schedule.prepare-cron`, `schedule.send-cron`(Asia/Seoul)을 쓴다.
  - 회차는 send-cron에서 계산한다.
  - 그래서 테스트용으로 "1분 뒤 준비, 3분 뒤 발송"처럼 바꿔도 그대로 동작한다.
- **enum 컬럼은 VARCHAR로 저장한다.**
  - MySQL 네이티브 `enum(...)`은 `ddl-auto: update`가 값 목록을 바꾸지 않아서, 새 상태값을 저장하면 실패한다.
  - Hibernate가 새로 만드는 테이블에는 `check (col in (...))`가 붙는다. 그런 DB에서 값을 추가할 때는 check를 직접 고쳐야 한다.
